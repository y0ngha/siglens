# 쉽게보기 — AI 분석 결과 평이화 레이어 설계

- 작성일: 2026-08-31
- 상태: 설계 확정
- 브랜치: `feat/plain-language-analysis`
- 선례: `src/entities/analysis-translation/` (동일 클래스의 후처리 레이어)

---

## 1. 문제

AI 분석 결과가 전문 어휘와 배경 지식을 전제해 비전문가가 읽기 어렵다.

각 분석 프롬프트에 "쉽게 써라"를 넣는 방식은 기각한다. 프롬프트 15개에 같은 지시를
복제하면 크기만 커지고, 톤 규칙을 고칠 때마다 전부를 고쳐야 하며, 분석 정확도를 위한
지시와 가독성을 위한 지시가 한 프롬프트 안에서 서로를 침식한다.

대신 **이미 생성된 분석 결과를 입력으로 받아 평이한 산문으로 다시 쓰는 후처리 레이어**를
하나 둔다. 분석 종류가 몇이든 함수 하나가 처리한다.

## 2. 범용성이 제1 제약이다

이 프로젝트에는 **스킬 파일이 82개** 있다.

| 카테고리 | 개수 |
|---|---|
| indicators | 37 |
| patterns | 17 |
| strategies | 8 |
| candlesticks | 7 |
| fundamental / news / support-resistance / _core | 13 |

여기서 파생되는 지표명·전략명·패턴명은 **108개**다(`skills/**/*.md`의 `name`·
`indicators` 필드에서 기계 추출). 프롬프트에 이것들을 열거하는 설계는 성립하지 않는다.

- 목록은 스킬이 추가될 때마다 반드시 뒤처진다. 이 레포의 `proseFields.ts` JSDoc이
  똑같은 이유로 손 목록을 거부한다.
- 실측으로 **효과도 없었다**(§9.2).

**따라서 프롬프트는 개별 이름을 하나도 언급하지 않는다.** 대신 "이름"이라는
**카테고리 자체**를 금지한다. 스킬이 200개가 되어도 그대로 유효하다.

같은 이유로 **글자 수·문단 수 제한도 두지 않는다.** 분석 타입마다 적정 분량이 다르고
(§9.3의 타입별 압축률 참고), 고정 숫자는 특정 타입에 맞춘 상수일 뿐이다.

## 3. 산출물 형태

"쉽게" 모드는 카드·표를 접고 **흐름이 있는 산문 한 덩어리**로 교체한다.
필드별 1:1 치환이 아니다 — 카드가 15개면 쉬운 말로 바꿔도 15개라 부담이 그대로 남고,
목표인 "읽어 내려가는 흐름"이 생기지 않는다.

## 4. 레포 분담 — siglens 단독

`docs/architecture/SCOPE.md` §0은 "AI 분석 프롬프트 변경"과 "응답 후처리 룰 추가"를
core로 보내지만, 같은 문서가 siglens 몫으로 명시하는 **"core가 노출하지 않는
프레젠테이션 전용 가공"**이 이 작업의 분류다.

- `src/entities/analysis-translation/`이 이미 같은 클래스다. 분석 결과의 산문만 뽑아
  DeepSeek으로 재작성하고, 내용 해시로 Redis에 캐시하고, 실패하면 원문으로 떨어진다.
  그 `api.ts` JSDoc이 siglens에 둔 이유를 적어두었다.
- core에 만들면 `extractProse`·DeepSeek 어댑터·캐시 패턴을 두 벌로 갖게 되고,
  배선을 고칠 때마다 교차 레포 릴리스가 붙는다.
- core 타입은 건드리지 않는다. `plain` 필드는 siglens가 소유하는 SSE 봉투에만 붙는다.

## 5. 아키텍처

### 5.1 신규 모듈

```
  lib/supersededPaths.ts     대체된 경로 제거 (§6.2)
  lib/guardPlainText.ts      shape · 숫자 · 길이 가드 (§7)
  lib/plainModel.ts          모델 + 그 provider의 서버 키를 한 자리에서 고른다
  index.ts

src/shared/
  lib/plainEnvelope.ts       readPlain() — SSE 봉투에서 산문을 꺼낸다
  model/analysisView.ts      전역 표시 모드 (localStorage)
  ui/PlainAnalysisSwitch.tsx 7개 위젯이 공유하는 토글 + 본문 스위치

  ui/AnalysisViewToggle.tsx  세그먼트 컨트롤(pill)
```

**공유 컴포넌트를 `shared`에 두는 이유.** 분석 위젯 7종이 모두 소비한다. 처음에는
`widgets/analysis/`에 뒀는데, 나머지 6개 탭을 배선하면서 widgets↔widgets 교차 import가
여섯 갈래로 늘어나 `shared`로 옮겼다.

### 5.1.1 모델 선택 — provider와 키를 함께 고른다

`tryReadTranslatorConfig`를 재사용하려다 실패했다. 그 함수는 **Gemini 전용**이다
(`GEMINI_API_KEY` + Gemini로 검증된 `TRANSLATE_MODEL`). 그 값을 `callDeepseekChat`에
넘기면 `[deepseek] Non-DeepSeek model spec: gemini-2.5-flash-lite`로 **매 호출이
던진다** — 로컬 브라우저 실증에서 잡혔고, 단위 테스트로는 잡히지 않았다(모킹이
가렸다).

`tryReadPlainModelConfig`는 모델을 정하고 core의 `getProviderForModel`로 provider를
판별해 그 provider의 서버 키를 고른다. 둘이 어긋날 수 없고, provider가 늘면 `never`
소진 검사가 컴파일에서 걸린다. 호출은 어댑터가 아니라 `callAiProviderRouter`로 한다.

⚠️ 기존 `src/entities/analysis-translation/api.ts`에 **같은 잠복 버그가 남아 있다** —
`ko`는 조기 반환이라 안 터지고 en·ja·zh만 조용히 한국어로 떨어진다. 이 PR 범위 밖이라
고치지 않았다.

### 5.3 데이터 흐름

```
run*Analysis()                                    ← 변경 없음
  ↓  (core filterAnalysisResult 통과한 결과)
Promise.all([
    translateAnalysisForLocale(result, locale),   ← 기존. 원본 뷰의 로케일 번역
    rewriteToPlainLanguage(result, locale),       ← 신규
])
  ↓
{ ...localized, plain }
  ↓
heartbeatStream(...)                              ← 기존
```

**병렬인 이유.** `rewriteToPlainLanguage`의 입력은 한국어 원문 산문이라 로케일 번역의
결과에 의존하지 않는다. 직렬 체이닝이면 추가 지연이 두 마감의 **합**이지만 병렬이면
**최댓값**이다. `ko`는 번역이 즉시 no-op이라 실질 상한이 45초다.

`heartbeatStream(work)`의 `work` 안에서 실행해야 한다. 바깥에서 await하면 첫 바이트까지의
침묵이 프록시 idle 한도에 걸린다(2026-08 실측: cloudflared 경유 125.9초).

### 5.4 티어 필터가 먼저다 (계약)

입력은 반드시 core `filterAnalysisResult`를 통과한 payload여야 한다.

필터 전 값을 넣으면 **유료 콘텐츠가 평문 산문으로 샌다.** 산출물이 문자열 한 덩어리라
사후 필드 마스킹이 불가능하다. 실측(캐시된 PLTR `member` 응답에 티어별 필터 적용):

| tier | prose 조각 | 문자 수 | lockedInfoDepth |
|---|---|---|---|
| free | 5 | 3,240 | `partial_detail, full_detail, entry, stoploss, target, confidence` |
| member | 21 | 4,913 | — |
| pro | 21 | 4,913 | — |

SSE 라우트에서 이 함수는 액션 결과 봉투(`{ result, lockedInfoDepth }`)를 받으므로
자연히 필터 뒤에 온다. 그 순서가 설계상 필수라 §10에 회귀 테스트를 둔다.

### 5.5 대상 분석 종류

`technical` · `overall` · `news` · `fundamental` · `financials` · `options` · `congress` — 7종.
서버(`PLAIN_ENABLED_TYPES`)와 클라이언트(각 탭 위젯) 양쪽이 전부 배선돼 있다.

`extractProse`가 응답 타입을 가리지 않고, 프롬프트에 타입별 분기가 없으므로 종류를
늘리는 비용은 허용 목록에 문자열 하나 + 그 탭 위젯을 `PlainAnalysisSwitch`로 감싸는 것이다.

제외: `marketNewsDigest` · `briefing` · `macroBriefing` — 토글 UI가 없어 호출이 낭비다.

**클라이언트 배선 형태.** 각 탭의 `fetch*`는 봉투를 벗기며 `plain`을 버리므로,
`readPlain(result)`로 꺼내 `WithPlain<T>`로 함께 나른다. `src/widgets/__tests__/plainWiring.test.tsx`가
다섯 탭을 한 번에 고정한다 — 어느 한 탭에서 `readPlain` 호출을 지우면 깨진다(뮤테이션 검증 완료).

## 6. 프롬프트

### 6.1 입력

```
prose:  { "summary": "…", "keyLevels.support.0.reason": "…", … }
facts:  { symbol, trend?, riskLevel?, numbers: [218.5, 241.0, …] }
```

`prose`는 `extractProse` 결과를 경로 키 맵으로 재구성한 것이다. 경로가 의미를 실어주므로
타입별 분기가 필요 없다. `trend`·`riskLevel`은 응답 타입에 따라 없을 수 있어 존재 검사
하나로 처리한다.

`facts.numbers`는 응답 객체를 전수 walk해 모은 숫자다. 모델이 써도 되는 숫자의
화이트리스트이자 §7 숫자 가드의 정답지다.

### 6.2 대체된 경로 제거

`actionRecommendation.reconciledLevels.{exit,riskReward}`는 core JSDoc상
"Regenerated ... reflecting the reconciled levels" — 형제 필드의 **재생성본**이다.
둘 다 넘기면 모델이 서로 다른 두 분석으로 착각한다. 실측 출력:

> "참고로 **다른 분석에서는** 목표가를 334.01달러, 손절을 308.97달러로 제시하기도 했는데"

한 화면에 모순된 매매 가격 두 벌이 나오는 상태다. 프롬프트 규칙이 아니라 입력에서
구조적으로 잘라낸다.

`reconciledLevels`가 있으면 제거: `actionRecommendation.exit`,
`actionRecommendation.riskReward`, `actionRecommendation.reconciledLevels.reason`
(마지막은 보정 사유 툴팁이라 독자용이 아니다). `actionRecommendation.entry`는 대응
재생성본이 없어 유지한다.

`extractProse`는 i18n 번역이 공유하므로 **수정하지 않는다.** 제거는 이 레이어에서 한다.

### 6.3 규칙 (확정판 = §9의 P5)

```
과한 어휘 없이, 과한 문장 없이, 읽기 쉽게, 편하게,
자연어·문어체 기반으로 사람이 읽기 쉬운 흐름으로 다시 써주세요.

- 지표, 전략, 패턴, 기법에 붙은 고유한 이름은 쓰지 마세요.
  영어 약어, 사람 이름에서 온 용어, 도형이나 사물에 빗댄 이름이 모두 여기 해당합니다.
  이름을 지우고, 그 이름이 가리키는 현상 자체를 우리말로 쓰세요.
  원본이 "무엇을 근거로" 판단했는지가 아니라 "무엇이 벌어지고 있는지"를 쓰는 것입니다.
- 읽는 사람은 주식 용어를 전혀 모릅니다. 설명 없이 등장하는 단어가
  하나라도 있으면 그 사람은 거기서 읽기를 멈춥니다.
- 이름을 우리말로 옮기는 것만으로는 부족합니다. 옮긴 말도 처음 듣는 사람에게는
  여전히 모르는 말입니다. 수치를 그대로 옮겨 적지 말고, 그 수치가 이 회사의 무엇을
  말해 주는지, 좋은 쪽인지 나쁜 쪽인지를 함께 쓰세요.
  독자가 궁금한 것은 "이 값이 얼마인가"가 아니라 "그래서 어떻다는 것인가"입니다.
- 원본의 항목을 하나씩 차례대로 옮기지 마세요. 원본이 여러 항목으로 나눠 말한 것을
  하나의 이야기로 엮어, 중요한 것부터 자연스럽게 이어 쓰세요.
- prose와 facts에 없는 숫자를 만들지 마세요. 퍼센트를 직접 계산하지 마세요.
- 원본에 있는 가격은 자릿수를 바꾸지 말고 그대로 옮기세요.
- 매수, 매도를 권유하는 단정적 표현을 쓰지 마세요.
- 마크다운, 불릿, 제목, 이모지를 쓰지 마세요. 문단으로만 씁니다.
- 완성된 글만 출력하세요. 인사말, 설명, 따옴표, 코드블록을 붙이지 마세요.
  문단 사이는 빈 줄로 구분합니다.
```

**지표명·스킬명 언급 0개. 글자수·문단수 제한 0개. 타입별 분기 0개.**

출력은 **평문**이다. JSON으로 감싸지 않는다 — 산출물이 문자열 하나라 봉투가 불필요하고,
실측에서 JSON 봉투는 파싱 실패 12.5%만 만들었다(§9.2).

## 7. 가드 — 전부 산출물 검사

프롬프트로 "숫자를 지어내지 마라"라고 부탁하는 것에 의존하지 않는다.

| 가드 | 판정 | 실패 시 |
|---|---|---|
| shape | 코드펜스를 벗긴 뒤 비어 있지 않은 문자열인가 | 재시도 1회 → `null` |
| 숫자 | 가격형 토큰이 허용 집합의 **반올림 표현**인가 | 재시도 1회 → `null` |
| 길이 | 입력 산문 길이 합의 20% 이상이고 200자 이상인가 | 재시도 1회 → `null` |

상한은 두지 않는다(§2).

### 7.1 숫자 판정

```
출력 토큰 x (소수 d자리)가 통과  ⟺  ∃ a ∈ allowed. round(a, d) === x
allowed = facts.numbers ∪ 입력 산문에 등장한 모든 숫자
가격형 토큰 = /(?<![\w.])(\d{1,3}(?:,\d{3})+(?:\.\d+)?|\d+\.\d+|\d{3,})(?![\d])/
```

**정확 일치가 아니라 반올림 일치인 이유.** 엄격 일치로 시작했다가 실측에서 오탐이 났다.
AMGN 출력의 `"431달러에서 434달러 사이"`는 원본 `431.29`·`433.68`을 반올림한 것인데
환각으로 잡혔다. 초보자용 글에서는 `431.29달러`보다 `431달러`가 나은 표현이므로
반올림은 막을 게 아니다.

**후행 lookahead가 `(?![\w])`가 아니라 `(?![\d])`인 이유.** `219,522.5B`처럼 단위
접미사가 붙으면 `(?![\w])`가 `B`에 걸려 `219,522`만 잘라내 비교한다. 원본에 정확히 있는
값이 위반으로 찍혔다.

작은 정수(`몇 주간`, `한 단계`)는 3자리 미만이라 애초에 토큰이 아니다.

### 7.2 음성 테스트

| 입력 | 판정 |
|---|---|
| `183.60달러` (원본 존재) | pass |
| `184달러` (183.60의 반올림) | pass |
| `219,522.5B` (단위 접미) | 원본에 있으면 pass |
| `183.65달러` (환각) | REJECT |
| `210달러` (환각 정수) | REJECT |
| `12.7%` (모델이 계산) | REJECT |

**한계.** `allowed`는 payload에서 긁어모은 숫자 가방이라, 모델이 만든 값이 우연히 다른
필드 값과 같으면 통과한다. 그래서 §6.3에 "퍼센트를 직접 계산하지 마세요"를 넣었다.
이 가드는 날조된 가격을 막는 도구이지 파생 계산의 정확성을 보장하지 않는다.

### 7.3 재시도

같은 프롬프트를 그대로 재전송하지 않는다. 실패한 가드를 지적하는 한 줄을 덧붙인다.
재시도는 §7.4의 45초 마감 **안에서** 이뤄진다 — 마감은 시도 횟수가 아니라 전체 예산이다.

### 7.4 마감

45초. `withDeadline`의 `Promise.race`가 끝난 뒤 붙는 레이어라 `STREAM_DEADLINE_MS`의
보호를 받지 못한다. `callDeepseekChat`은 timeout·maxRetries를 지정하지 않아 OpenAI SDK
기본값(10분 × 3회)을 쓰므로, 프로바이더가 매달리면 스트림 하나가 동시성 슬롯을 30분
붙들고 배포 시 SIGTERM 드레인(180초)을 넘긴다.

## 8. 캐시

```
plain:v1:{locale}:{sha256(JSON.stringify({ prose, facts }))}
```

TTL 30일. `analysis-translation`의 `i18n:analysis:v1:{locale}:{digest}`와 동일한 내용
주소 방식이다. 심볼·모델·타임프레임을 넣지 않는다 — 같은 입력이면 결과가 같고, 입력이
바뀌면 해시가 달라져 스스로 무효화된다.

**티어를 키에 넣지 않는다 — 내용 해시가 이미 가른다.** 필터된 payload를 해시하므로
free와 member는 자동으로 다른 키를 얻는다. 실측(앞 16자):

```
free    fc7a8be9134078f5
member  3f7c2d189181f055
pro     3f7c2d189181f055
```

member와 pro가 같은 것은 leak이 아니라 정확한 동작이다 — 필터 결과가 실제로 동일하므로
같은 문장을 공유해야 맞다. 티어 세그먼트를 넣으면 이 공유가 깨져 호출이 두 배가 된다.

`v1`은 프롬프트 버전이다. §6.3을 고치면 반드시 올린다.

## 10. UI

### 10.1 토글

전역 세그먼트 컨트롤(pill) 하나. 탭이 아니다 — 최상위 탭 9개가 이미 URL 라우트라
중첩 탭이 되고, 무엇보다 쉽게/원본은 다른 내용이 아니라 같은 내용의 다른 표현이다.

```

├────────────────────────────────────────────┤

│  ────────────────────────────────────────  │
│  애플은 지금 오름세가 이어지는 중입니다…      │
│                                            │
│  ┌──────────────────────────────────┐     │
│  │ 지표·패턴까지 자세히 보기 →        │     │  ← 하단 CTA
│  └──────────────────────────────────┘     │
└────────────────────────────────────────────┘
```

### 10.2 상태

```ts
usePersistentState<'plain' | 'raw'>('siglens:analysis-view', 'plain')
```

기본값 `'plain'`. `usePersistentState`는 `useSyncExternalStore` 기반이라 같은 key를 쓰는
인스턴스끼리 자동 동기화되고 다른 탭 변경도 반영된다 — 데스크톱 패널과
`MobileAnalysisSheet`가 상태를 공유해야 하므로 이 성질이 필요하다.

전역 하나만 둔다. 탭별 상태를 따로 두면 사용자가 같은 선택을 9번 해야 한다.
하단 CTA도 **같은 전역 상태를 바꾼다** — "이 페이지만 원본" 같은 두 번째 상태를 만들지 않는다.

### 10.3 컴포넌트

- `src/widgets/analysis/PlainAnalysisView.tsx` — `plain`을 빈 줄로 쪼개 문단 렌더 + 하단 CTA
- `src/widgets/analysis/AnalysisViewToggle.tsx` — pill. 패널과 모바일 시트가 공유
- `plain === null`이면 pill을 렌더하지 않고 원본을 표시한다
- `lockedInfoDepth`가 비어 있지 않으면 쉽게보기에서도 페이월 안내를 렌더한다.
  free 티어의 산문은 진입가·손절·목표가가 빠진 상태고, 원본 뷰의 잠금 카드를 쓸 수 없다
  (카드가 없다). 빠뜨리면 free 사용자는 잠긴 항목이 있다는 사실 자체를 모른다.

`widgets.analysis.viewToggle.{plain,raw,cta}`

## 11. SEO — 1차에서는 건드리지 않는다

봇과 콜드 방문자의 초기 HTML은 `seo_analysis_snapshots` 행을 `*SnapshotProse.tsx` 7종이
서버 렌더한 것이다. 라이브 분석은 SSE 클라이언트 fetch라 애초에 색인되지 않는다.

1차에서는 이 경로를 **전혀 수정하지 않는다.** `plain`은 SSE 응답에만 실리므로 색인 변화가
0이고, 서버 렌더 내용이 클라이언트에서 교체되지 않으므로 CLS도 없다.

근거는 리스크 비대칭이다. 봇이 보는 본문을 바꾸면 색인 전체에 영향이 가고 확인까지 수 주가
걸린다. 특히 평이화는 본문 분량을 줄이는 방향이라(§9.4의 압축률 70%), 2026-07 thin 콘텐츠
노출 절벽에서 회복한 상태를 되돌릴 수 있다.

Phase 2(별도 스펙)에서 다룬다.
