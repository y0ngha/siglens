R6 review of `feat/i18n-multilingual` (worktree `/Users/y0ngha/Project/siglens-i18n`). **Approved — zero findings.** This closes the 6-round locale-prefix-breaks-path-logic bug class that started at [[project-i18n-multilingual-r1]] finding #5.

R5's consolidation (`src/shared/i18n/useAppPathname.ts` — wraps `usePathname()` + `splitLocalePath(...).path`) verified correctly applied to `SymbolTabs.tsx`, `NoticePopup.tsx`, `usePageContextLabel.ts`, `HeaderNav.tsx`, `HeaderMobileMenu.tsx`; all 4 functional fixes traced end-to-end (tab active-state comparison, `notices.path_pattern` matching via `useNoticePopup(pathname)`, `derivePageContextLabel`'s anchored regex, `isHrefActive`/`isVerticalActive` exact-match) and confirmed each consumer now receives a bare (locale-stripped) path.

**Audit test (`useAppPathname.test.ts`) verified sound, not a rubber stamp.** Its `grep -rln 'usePathname' src ... || true` step is a coarse substring scan (catches comment mentions too — confirmed via live run that `FearGreedRouteBody.tsx`, `RegionTabs.tsx`, `navigation.ts`'s destructuring, `LocaleContext.tsx`'s JSDoc, `locales.ts`'s JSDoc all substring-match but get correctly filtered out by the second regex step `/^\s*import\b.*usePathname/m`, which only fires on an actual `import ... usePathname` line). The `|| true` only guards grep's exit-1-on-no-match case, not a pass-through of real offenders. All 6 `ALLOWED_RAW_PATHNAME_USERS` entries verified individually by reading the file: `useQueryParamState.ts`/`useSectorSignalState.ts`/`useBacktestFilter.ts` all reuse raw (prefixed) `usePathname()` to rebuild the current URL for `router.push`/`replace` — correctly need the prefix; `AuthSessionHeaderClient.tsx` only uses it as a ref-compared change-detection key (`syncedPathRef.current === pathname`), never for matching/building — prefix-agnostic by construction; `LocaleSwitcher.tsx` imports `usePathname` from `@/shared/i18n/navigation` (next-intl's `createNavigation`, confirmed via its own source: `export const { ..., usePathname, ... } = createNavigation(routing)`), which is **already locale-stripped** by next-intl's own mechanism — a different, already-safe source, not the raw one the audit is meant to catch, but still needed in the allowlist because the test's grep is import-line-based, not source-module-aware.

**Broader sweep for (b), all clean:** grepped whole repo (not just modified_files) for `window.location.pathname`, `nextUrl.pathname`, `referer`/`document.referrer`, `headers().get(...)`, path-shaped `localStorage`/`cookies()` usage — zero hits outside test files. `runPrewarmBatch.ts` (seo-prewarm cron) uses `revalidateTag`, not URL-based fetches — locale-agnostic by construction, no finding. E2E specs (`notice-popup.spec.ts`, `symbol-tabs.spec.ts`, `header-mobile-nav.spec.ts`) all `page.goto()` only the default (ko, unprefixed) locale — a pre-existing coverage gap (e2e has never tested non-default locales across this whole epic), not a regression from this round, not flagged.

**Verification technique reused:** ran the actual grep pipeline from the audit test by hand (`grep -rln 'usePathname' src --include=...`) rather than trusting the test's green result alone, to independently confirm which files it candidate-matches and why each is filtered — this is what surfaced the "audit test is import-line-based, not module-aware" nuance (LocaleSwitcher needs an allowlist entry despite importing an already-safe wrapper).
