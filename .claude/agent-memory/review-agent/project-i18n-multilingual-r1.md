R1 review of `feat/i18n-multilingual` (worktree `/Users/y0ngha/Project/siglens-i18n`, next-intl 4.13.7 + Next 16.2.12). Design doc already approved in a separate round; this covered the CODE only.

**Key findings (all verified live, not speculative):**

1. **Locale-invariant canonical, 9 files.** `market`, `market/kr`, `fear-greed`, `fear-greed/kr`, `economy`, `economy/kr`, `news`, `news/us`, `news/[category]` all do `canonical: degraded ? null : MODULE_LEVEL_URL_CONST` where the const is `${SITE_URL}${path}` computed once at module load with no locale. Passing a concrete (non-`undefined`) `canonical` to `localeAlternates`/`localeAlternatesFrom` **bypasses** their self-referencing-canonical auto-derivation (`options.canonical === undefined ? localeCanonical(locale, path) : options.canonical`). Result: `/en/economy` etc. always canonicals to the ko URL. `backtesting/page.tsx` (omits `canonical` entirely) and `symbolMetadataFromSeo` (threads `locale` through) are the correct reference patterns. Fix is one line per file: `canonical: degraded ? null : undefined`. `localeCoverage.test.ts`'s regex safety net (`/localeAlternatesFrom|localeAlternates\(|symbolMetadataFromSeo\(/`) only checks the function name appears in source — doesn't verify the canonical arg is actually locale-derived, which is why this slipped through.

2. **`setRequestLocale` only in root `[locale]/layout.tsx`.** Design doc explicitly mandates calling it in "모든 레이아웃/페이지" and promises a route-inventory test asserting static rendering — neither exists beyond root layout; `localeCoverage.test.ts` never checks for `setRequestLocale`. Traced next-intl's actual mechanism in `node_modules/next-intl/dist/esm/.../RequestLocale.js`: `getRequestLocale()` checks `getCachedRequestLocale()` (React `cache()`, set only by `setRequestLocale`) and falls back to `headers()` — which throws `DYNAMIC_SERVER_USAGE` during static rendering. Currently masked (grep confirmed zero `getTranslations`/`getMessages` calls outside root layout — only `LocaleSwitcher.tsx` uses next-intl and it's client-side, reads from React context not the server cache), so no *current* runtime break, but it's the exact landmine the repo's own comment calls "이 레포에서 가장 비싼 실수다" for the next translated-content phase.

3. **`scripts/i18n/extract.mjs --apply` can emit broken code.** `classify()` in `lib/context.mjs` returns `applicable: true` for JSX/string candidates inside an enclosing component WITHOUT checking `component.body.type === 'BlockStatement'`. The text-replacement edit (`{t('key')}`) is queued unconditionally in extract.mjs's first pass; only in the *second* pass (over `componentsNeedingTranslator`) does it discover an expression-bodied arrow component (`const Foo = () => <div>한글</div>`) can't receive an injected `const t = ...` declaration, and skips *that* — but never retracts the already-queued replacement. Net effect: `t` referenced with no declaration/import → guaranteed compile/runtime failure. Root cause fix belongs in `classify()`, not extract.mjs's second pass.

4. **`scripts/i18n/{extract,translate,verify,lint,routes}.mjs` + `lib/{context,scan}.mjs` are gitignored** (`.gitignore` line 79 `/scripts/**` blanket-ignores `scripts/`, and unlike every other reusable script there, no `!/scripts/i18n/**` exception was added). `package.json` wires 5 `i18n:*` scripts to these paths — they'll vanish on fresh checkout/CI, exactly the failure mode the repo's own `.gitignore` comments warn about for other scripts (`seed-kr-listed-names.ts` etc.).

5. **`HeaderMobileMenu.tsx` (in-scope) + sibling `HeaderNav.tsx` (untouched but same regression)** import `usePathname` from `next/navigation` (locale-prefixed) instead of `@/shared/i18n/navigation` (locale-stripped, confirmed via next-intl's `useBasePathname.js`). `isHrefActive` does exact-string match against locale-unprefixed `NAV_TREE` hrefs → nav active-state highlighting breaks for every non-default locale. `LocaleSwitcher.tsx` already does it the right way (evidence the correct pattern exists in-repo).
