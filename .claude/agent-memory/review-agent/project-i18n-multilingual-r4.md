R4 review of `feat/i18n-multilingual` (worktree `/Users/y0ngha/Project/siglens-i18n`). Both R3 findings verified fixed correctly: `useTimeframeChange.ts:105-111` now wraps `window.history.replaceState` with `toLocalePath(...)` and lists it in the effect deps; all 15 Server Action `redirect()` call sites (logout, account-delete, oauth cancel/finalize×9, password-reset confirm, api-key save/delete×2, login, signup) now route through `src/shared/i18n/localeRedirect.ts`'s `localeHref`/`localeRedirect`. Verified the two documented "return vs await" JS-promise-adoption patterns are applied correctly and consistently: sites without a try/catch guard use `return localeRedirect(path)`; sites where a local catch re-throws `NEXT_REDIRECT` also correctly use `return localeRedirect(...)` (which — confirmed via JS async-function spec reasoning, not just trusting the JSDoc — *bypasses* the local catch entirely by adopting the promise at the `return` statement, before any later rejection occurs) except `loginAction.ts`/`registerAction.ts` which use the documented alternate `redirect(await localeHref(...))` form. `localeHref`'s idempotency (`splitLocalePath` strip-then-`localePath` re-apply) was checked for the "path segment legitimately equals a locale code" edge case flagged by the task prompt: confirmed NOT a bug, because `proxy.ts`'s `RESERVED_FIRST_SEGMENTS` (includes `...LOCALES`) plus its 301 uppercase-ticker-canonicalization guarantee every symbol reaching client code is already uppercase before `useLocalePath`/`LocaleLink`/`localeHref` ever see it, and `isLocale()` is a case-sensitive lowercase-only check — no real collision path exists client-side (this invariant is pre-existing from R1, not introduced this round).

**New required finding — `resolvePostSignupDestination` exact-match `'/'` comparison breaks post-signup onboarding redirect for every non-ko locale.**
`src/shared/lib/auth/redirect.ts:27-28`: `return next === DEFAULT_REDIRECT_PATH ? POST_SIGNUP_ONBOARDING_PATH : next;` (`DEFAULT_REDIRECT_PATH = '/'`). This round's `LoginContent.tsx`/`SignupContent.tsx` change (`next = toLocalePath(sanitizeNextPath(params.get('next')))`) means a brand-new EN/JA/ZH signup with **no specific return target** now produces `next = '/en'` (not `'/'`) — confirmed by executing `localePath('en','/')` directly: returns `/en`. `SignupForm.tsx:212-213`/`LoginForm.tsx:32` render the hidden `next` field whenever the prop is truthy, so `/en` (non-empty) IS submitted, unlike the ko case where `nextParam` is `undefined` and the field is omitted. Traced end-to-end through both signup paths: `registerAction.ts:145` (`resolvePostSignupDestination(next)` with `next='/en'` from the form) and `finalizeOAuthSignupAction.ts:143` (same, via `consumed.next` persisted from `SocialLoginButtons.tsx` → `/api/auth/[provider]/start` → OAuth state → callback → pending-signup store, all pass-through with no additional transformation). Since `'/en' !== '/'`, the function returns `/en` unchanged instead of routing to onboarding — new non-ko-locale members land on the locale home page instead of `/en/onboarding`, silently breaking the documented product policy ("a brand-new member with no specific return target lands on the holdings onboarding screen") for 3 of 4 locales. Login (not signup) does not have this bug — `loginAction.ts` has no onboarding-redirect branch, it just forwards `next` through `localeHref`.

**Why the 10304-passing baseline didn't catch it — test-masking, both files affected:** `src/features/auth-oauth-consent/__tests__/actions/finalizeOAuthSignupAction.test.ts:52-57` does `vi.mock('@/shared/lib/auth/redirect', () => ({ sanitizeNextPath: ..., resolvePostSignupDestination: vi.fn((next) => next === '/' ? '/onboarding' : next) }))` — a **literal reimplementation of the exact same buggy comparison** as a mock, so the real production function is never invoked by this test file at all (MISTAKES.md #13.5 "redefining production functions locally in tests" — doubly bad here since the redefinition also perfectly reproduces the bug, making it un-catchable no matter what `next` value the test feeds in). `src/features/auth-signup/__tests__/actions/registerAction.test.ts` does NOT mock `resolvePostSignupDestination` (uses the real function), but its `getLocale` is pinned to `'ko'` (per the file's own comment: "그러면 리다이렉트 경로가 접두사 없는 기존 값과 같아져 기존 단언이 그대로 유효하다") and no test case ever feeds a locale-prefixed `next` like `/en` as form input — so the real bug path is simply never exercised, not masked by a mock. This directly answers the task prompt's question "could the vi.mock('next-intl/server') additions hide a real regression" — yes, in combination with (for the OAuth file) a second mock that duplicates the bug, and (for both files) the absence of any locale-prefixed-`next` test case.

**Verified NOT a bug (checked, no finding):** the `nextParam = next === '/' ? undefined : next` line in both `LoginContent.tsx:36` and `SignupContent.tsx:20` is the exact same class of comparison but is *correct* there — it only controls whether the hidden field is rendered at all (an optimization/parity-with-old-behavior nicety), and login has no downstream code path that depends on distinguishing "true empty" from "locale home." Only the signup-specific `resolvePostSignupDestination` mapping breaks.

**Recommended (pre-existing gap, not a regression from this round, likely deliberately unreached yet):** `src/entities/email-token/templates/passwordResetEmail.ts:24,32` hardcodes `RESET_PATH = '/reset-password'` with no locale prefix, and the entire email (subject/text/html, `lang="ko"`) is Korean-only regardless of the recipient's site locale — same "whole content-translation phase not yet reached" category as R2's deferred JSON-LD finding. Not in this round's `modified_files` and not part of the navigation-locale-loss class this epic has been fixing (the link's own missing prefix is moot given the surrounding email text is 100% Korean either way), so flagged as recommended follow-up rather than required.
